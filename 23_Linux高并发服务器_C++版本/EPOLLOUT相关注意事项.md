这是一个非常核心的 `epoll` 编程问题！理解了这一点，你就彻底掌握了 `epoll` 写事件的管理精髓。

直接回答你的问题：**如果应用层发送队列清空了，不立刻取消 `EPOLLOUT`，会导致 `epoll_wait` 陷入死循环，瞬间把 CPU 打满 100%。**

下面为你详细拆解背后的底层逻辑。

### 一、 `EPOLLOUT` 的触发条件是什么？

在 `epoll` 模型中，`EPOLLOUT`（可写事件）的触发条件是：**Socket 的内核发送缓冲区有剩余空间（未满）。**

### 二、 为什么不能一直开着 `EPOLLOUT`？

假设你的应用层发送队列空了，但你依然在 `epoll` 中注册了 `EPOLLOUT`。

1. **常态**：对于 TCP 连接来说，只要对端正常接收数据，本端的内核发送缓冲区绝大部分时间**都是不满的**（有剩余空间）。
2. **死循环形成**：因为缓冲区有剩余空间，`epoll_wait` 会**立刻、不断地**返回，告诉你“你可以写了！”。
3. **你的程序逻辑**：
   ```c
   if (events[i].events & EPOLLOUT) {
       // 检查应用层发送队列...
       if (queue_is_empty()) {
           // 没数据可发，什么都不做
           continue; 
       }
   }
   ```
4. **灾难**：你的程序啥也没干，但 `epoll_wait` 一直在唤醒它。CPU 占用率瞬间飙升到 100%，全用来跑空循环了。这在网络编程中被称为 **忙等待**。

### 三、 正确的做法：按需注册（动态修改）

正确的架构设计是：**平时只关注读事件，只有当写数据遇到阻碍（缓冲区满）时，才临时开启写事件。**

完整的发送状态机如下：

#### 阶段 1：正常发送（队列非空，缓冲区未满）
调用 `write()`，数据成功写入内核。此时不需要开启 `EPOLLOUT`。

#### 阶段 2：遇到阻碍（队列非空，缓冲区满了）
调用 `write()` 返回 `-1`，`errno == EAGAIN`。
此时必须将未发完的数据**暂存到应用层发送队列**，并向 `epoll` 注册写事件：
```c
// 修改 epoll 事件：加上 EPOLLOUT
struct epoll_event ev;
ev.events = EPOLLIN | EPOLLOUT | EPOLLET; 
epoll_ctl(epfd, EPOLL_CTL_MOD, fd, &ev);
```

#### 阶段 3：缓冲区可写（继续发送）
下次 `epoll_wait` 返回 `EPOLLOUT`，程序被唤醒，取出应用层队列的数据继续 `write()`。

#### 阶段 4：队列清空（发送完成）
一旦发现应用层队列空了，**必须立刻取消 `EPOLLOUT`**，改回默认状态：
```c
// 改回只关注读事件
struct epoll_event ev;
ev.events = EPOLLIN | EPOLLET; 
epoll_ctl(epfd, EPOLL_CTL_MOD, fd, &ev);
```

### 四、 为什么保留 `EPOLLIN | EPOLLET`？

当发送队列清空后，我们要取消写事件，但**绝对不能关闭读事件**。
*   **保留 `EPOLLIN`**：因为即使你在往外发数据，客户端依然可能随时给你发数据进来。必须保持对读事件的监听。
*   **保留 `EPOLLET`**：这是边缘触发模式。只有在状态变化时才通知（例如新数据到达）。这保证了即使你没读完缓冲区的数据，`epoll` 也不会像 LT 模式那样死命唤醒你。

### 总结

在 `epoll` 中管理写事件的**黄金法则**是：
**`EPOLLOUT` 不能常开，它是“租来的”。只有当 `write` 遇到 `EAGAIN` 时才去“借”来用一下；一旦应用层队列清空，必须立刻“还”回去（取消注册）。** 这样才能兼顾数据不丢失与 CPU 不空转。
