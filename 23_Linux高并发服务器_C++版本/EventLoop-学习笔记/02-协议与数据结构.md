# 02 · 协议与数据结构

## 1. 应用层协议：4 字节定长头 + 包体

TCP 只是字节流，没有"消息边界"。所以每个自定义协议都要自己定边界。这里用的是最经典的一种：**长度前缀**。

```
 0        1        2        3        4                      4+body_len
 +--------+--------+--------+--------+---------------------------+
 |   msg_type (2B)  |   body_len (2B) |          body             |
 +--------+--------+--------+--------+---------------------------+
   \_____________/    \___________/
     网络字节序(大端)     网络字节序(大端)
```

| 偏移 | 长度 | 字段 | 说明 |
| --- | --- | --- | --- |
| 0 | 2 | `msg_type` | 消息类型/业务 ID（`session.h:53` 注释：1001 登录、1002 聊天）。接收方回显时原样带回 |
| 2 | 2 | `body_len` | 包体字节数，**上限 `BUFF_SIZE = 2048`**（`global.h`），超了直接断连接 |
| 4 | body_len | `body` | 原始字节，本项目当纯字节处理，不解析内容 |

相关常量（`global.h`）：

```c
#define BUFF_SIZE 2048    // 包体上限，也是长度校验阈值
#define HEAD_LEN 4        // 头长度 = 2(type) + 2(len)
#define HEAD_ID_LEN 2     // 未使用（死宏）
#define HEAD_LEN_LEN 2    // 未使用（死宏）
```

**为什么是 4 字节小头而不是大 JSON？** 因为要先用固定长度把"后面还有多少字节"读出来，才能知道包边界。头必须定长，这是长度前缀协议的基本要求。

**为什么 `body_len` 用 `uint16_t`？** 省空间，但上限就锁死在 65535；这里又额外把上限压到 2048。想支持大消息就得改成 uint32 或"分片 + 组装"。

**字节序**：发送端 `htons`（`session.cpp:40-42`），接收端 `ntohs`（`io_thread.cpp` 解析处）。网络字节序是大端，本机可能是小端，必须转，否则长度字段会读出一个荒谬的值（比如 2048 变成 8 或 524288）。

## 3. 逐个讲解

### 3.1 `IOTask`：跨线程传递的唯一载体（`io_thread.h:29`）

```cpp
enum class TaskType { RegisterConn, SendData, Shutdown };

class IOTask {
public:
    IOTask(int fd, TaskType type, std::string data = "", int msgtype = 0);
    TaskType _type;
    int _fd;
    std::string _data;   // 仅 SendData 使用
    int _msgtype;
};
```

三种任务：

| 任务 | 谁产生 | 谁消费 | 语义 |
| --- | --- | --- | --- |
| `RegisterConn` | 主线程（accept 之后） | IO 线程 | "把 fd 变成我的连接：`new Session` + 设非阻塞 + 注册 `EPOLLIN\|EPOLLET`" |
| `SendData` | 任意线程调用 `Session::Send` | 目标 IO 线程 | "把这个 fd 的数据发出去" |
| `Shutdown` | `IOThread::stop()` | IO 线程 | "退出你的 loop" |

注意 `_data` 是 **`std::string` 值拷贝**：跨线程传数据必须拷贝或转移所有权，绝不能传裸指针（原对象的生命周期由另一个线程说了算）。用 `std::string` 还顺便解决了"字节里含 `\0`"的问题（`std::string` 能存任意二进制，长度靠 `size()`）。

### 3.2 `HeadBuf`：只为收头而生的小缓冲（`session.cpp:5`）

```cpp
HeadBuf::HeadBuf(size_t head_len) : _head_len(head_len), _offset(0) {
    _buf = (char*)malloc(sizeof(char) * head_len);   // 4 字节
}
```

它存在的意义：**头只有 4 字节，可能分两次才读全**。所以需要一个"已经攒了几个字节"的偏移量 `_offset`，配合状态 `HEAD_RECVING` 实现"半包头"续读。

用一个 `shared_ptr` 包着 4 字节而不是直接 `char _head[4]` 的数组，是为了和 `DataBuf` 保持一致的写法（也方便后面 `make_shared`）。

### 3.3 `DataBuf`：既能收也能发的缓冲（`session.cpp:22`、`session.cpp:32`）

两个构造函数对应两个方向，这是最容易看错的地方：

```cpp
// ① 接收用：只分配 body 空间，_buf 里【不含头】
DataBuf(uint16_t type, size_t data_len)
    : _data_len(data_len), _type(type), _offset(0) { _buf = malloc(data_len); }

// ② 发送用：一次分配 4+data_len，并【自动把协议头写进去】
DataBuf(uint16_t type, std::string data, size_t data_len)
    : _data_len(HEAD_LEN + data_len), _type(type), _offset(0) {
    _buf = malloc(_data_len);
    uint16_t net_type = htons(type);
    uint16_t net_len  = htons(data_len);
    memcpy(_buf,   &net_type, 2);   // 头：type
    memcpy(_buf+2, &net_len,  2);   // 头：len
    memcpy(_buf+4, data.data(), data_len);  // 体
}
```

| 方向 | `_buf` 内容 | `_data_len` | `_offset` 含义 |
| --- | --- | --- | --- |
| 收 | 纯 body | body 长度 | 已收到多少字节 |
| 发 | `[4B 头][body]` | `4 + body 长度` | 已发出多少字节 |

**"发送缓冲自带协议头"是个好设计**：写 socket 时不用再拼一次，也避免了"头和数据分两次 write 导致对端收到两个半包"的复杂度。代价就是两个构造函数语义不对称，读的时候必须分清。

### 3.4 `Session`：一条连接的全部状态（`session.h:63`）

```cpp
class Session {
    friend class IOThread;          // IOThread 是唯一能碰私有成员的人
public:
    Session(int fd, IOThread* pthread);
    void Send(std::string data, int msg_type);   // 公开的、线程安全的发送入口
private:
    int _fd;
    std::shared_ptr<DataBuf> _data_buf;   // 收体缓冲（收完置 nullptr）
    std::shared_ptr<HeadBuf> _head_buf;   // 收头缓冲（长期存在）
    enum RecvStage _recv_stage;           // NO_RECV / HEAD_RECVING / BODY_RECVING
    enum SendStage _send_stage;           // NO_SEND / SENDING
    std::mutex _send_mtx;                 // 死代码
    std::queue<std::shared_ptr<DataBuf>> _send_que;   // 待发队列
    IOThread* _p_ownerthread;             // 回指所属线程，用来投递发送任务
};
```

关键点：

- 用 **组合**（`shared_ptr<HeadBuf>` 而不是继承）而不是继承，是为了让 `HeadBuf`/`DataBuf` 可以独立复用；
- `_p_ownerthread` 是**裸指针**：因为 `IOThread` 的生命周期严格长于它创建的 `Session`（IO 线程比它的所有连接活得久），所以不需要 `shared_ptr`。这是"能用裸指针就用裸指针表达非拥有关系"的合理取舍。
- `Send()` 是**唯一对外的写入口**，而且它自己不做 IO，只是把任务投递给 owner 线程 → 天然线程安全。

### 3.5 状态机一览

```
收:  NO_RECV ──读头(全)──► BODY_RECVING ──读体(全)──► NO_RECV     （循环）
        │                        │
        └─读头(半)─► HEAD_RECVING ┘  ← 两种状态都进"继续读头"的分支

发:  NO_SEND ──send_data()/handle_epollout() 进入──► SENDING ──Defer 析构──► NO_SEND
```

`RecvStage` 有 3 个值但"读头分支"把 `NO_RECV` 和 `HEAD_RECVING` 合并处理（`io_thread.cpp:499`），这是刻意的：初次收头和续收半截头本来就是同一件事。

## 4. 内存所有权表（这张表能解决 90% 的"这里会不会悬空指针"疑问）

| 对象 | 谁创建 | 谁长期持有 | 谁是临时持有者 | 释放时机 |
| --- | --- | --- | --- | --- |
| `IOTask` | 投递方 `make_shared` | 无（队列里短暂存在） | `_tasks` 队列 / `deal_enque_tasks` 的局部 `q` / 循环变量 `task` | 处理完出作用域即销毁 |
| `Session` | IO 线程处理 `RegisterConn` 时 `make_shared` | `IOThread::_sessions[fd]` | `loop()` 里的局部 `sess`；`handle_epollout` 的参数与 `Defer` 捕获 | 从 `_sessions` 中 `erase` 且所有临时持有者释放后 |
| `HeadBuf` | `Session` 构造时 `make_shared` | `Session::_head_buf` | — | Session 销毁时 |
| `DataBuf`（收） | `read_head_data` 解析完头时 `make_shared` | `Session::_data_buf` | 局部 `sess` | 收完一包后立即 `= NULL`，因此提前释放 |
| `DataBuf`（发） | `deal_enque_tasks` 里 `make_shared` | `Session::_send_que` | `send_data`/`handle_epollout` 的局部变量 | 队列弹出后释放 |

**`shared_ptr` 在这里不是"为了炫技"，而是为了保命**（第 4 章会看到 `handle_epollout` 里那个 `Defer defer([sess](){...})` 捕获的正是这个 `shared_ptr`：即使函数中途把连接从 `_sessions` 里删掉，对象也不会被销毁）。
