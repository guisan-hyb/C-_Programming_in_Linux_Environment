# 06 · 生命周期、错误处理与已知缺陷

## 1. 关闭时序：从 Ctrl-C 到所有线程退出

这是理解这份代码"谁管谁"的最好练习。请对照 `main.cpp:10`、`server.cpp:77/202`、`event_loop.cpp:22/32`、`io_thread.cpp:132/139`。

```
① 你按 Ctrl-C
② 内核 → signal_handler(SIGINT)                  main.cpp:10
③ 打印 "Received signal 2, stopping server..."
④ g_server->stop()                               server.cpp:202
     _stop = true;
     write(_event_fd, 1)         ← 只做一件事：把主线程从 epoll_wait 里叫醒
⑤ 主线程 run() 的 epoll_wait 返回，命中 fd == _event_fd
     打印 "receive exit eventfd" → return         server.cpp:135
⑥ main() 返回 → 局部对象 server 析构 → ~Server   server.cpp:77
     ├─ _loop->StopIOThread()                    event_loop.cpp:32
     │    └─ 对每个 IOThread 调 stop()：
     │         _stop = true; 入队 Shutdown 任务; write(自己的 eventfd, 1)
     ├─ free(_event_addr)
     ├─ close(_listen_fd / _event_fd / _epoll_fd)
     └─ 打印 "Server exit"
⑦ 【构造函数体结束后】成员按【声明逆序】析构 → _loop 最后声明，最先析构
     ~EventLoop                                  event_loop.cpp:22
       └─ 对每个线程 join() → 打印 "IOThread join exit"
       └─ 打印 "EventLoop exit"
     IOThread 对象销毁 → 每个打印 "IOThread 【i】exit"
```

### 两个关键认知

**认知一：`std::thread` 析构前必须 join 或 detach，否则程序直接 `std::terminate`。**
这里能安全 join，是因为 `StopIOThread()` 提前让每个线程"有路可退"（入队 Shutdown 任务 + 唤醒）。
**如果忘了 `StopIOThread` 直接 join，IO 线程还阻塞在 `epoll_wait` 上，`join()` 会永久挂住** —— 程序看上去"卡死在退出时"。这是多线程服务器最常见的退出 bug。

**认知二：`~Server` 的"函数体"和"成员析构"是两段。**
`StopIOThread()` 写在函数体里、`join()` 发生在成员析构阶段（`~EventLoop`），所以打印顺序一定是 `Server exit` 在 `IOThread join exit` 之前。看到这个顺序才知道自己读对了。

## 2. 资源所有权与释放

| 资源 | 谁分配 | 谁释放 | 现状 |
| --- | --- | --- | --- |
| `Server::_listen_fd` | `create_and_bind()` | `~Server` 函数体 `close` | ✅ |
| `Server::_event_fd` / `_epoll_fd` | 构造函数 | `~Server` 函数体 `close` | ✅ |
| `Server::_event_addr` | 构造函数 `malloc` | `~Server` 函数体 `free` | ✅ |
| 客户端 fd | 主线程 `accept` | `clear_fd()` 里 `close`；或进程退出由内核回收 | ⚠️ 退出时未显式 close |
| `IOThread::_event_fd` / `_epoll_fd` | `IOThread` 构造函数 | **没人释放** | ❌ 泄漏（`~IOThread` 只打印一行） |
| `IOThread::_event_addr` | 构造函数 `malloc` | **没人释放** | ❌ 每线程泄漏约 1024×12B ≈ 12KB |
| `Session` / `HeadBuf` / `DataBuf` | `make_shared` | `shared_ptr` 引用计数归零时 | ✅ |
| `_send_que` 里没发出去的数据 | `make_shared` | `Session` 销毁时随队列一起释放 | ✅ |

泄漏的规模对"跑起来学习"没有影响（线程退出时进程也快结束了），但**"析构函数不释放自己申请的资源"是必须改掉的习惯**，第 8 章的阶段 7 会让你补。

## 3. 已知缺陷清单

严重度：🔴 会导致功能错误 / 🟡 代码质量与健壮性 / ⚪ 只在极端情况出现。

| # | 级别 | 位置 | 现象与原因 | 复现方法 | 建议修法 |
| --- | --- | --- | --- | --- | --- |
| D1 | 🔴 | `read_body_data`（`io_thread.cpp:313`） | **发一个 `body_len == 0` 的包，连接会被服务端断开**。因为 `remain = 0` 时 `read(fd, buf, 0)` 返回 `0`，代码把 `0` 解释成"对端关闭" → `IO_ERROR` | `python3 echo_client.py zero` | 在 `read_head_data` 里 `body_len == 0` 时直接当完整包处理（回显 + 复位状态），不要进入 `BODY_RECVING` |
| D2 | 🟡 | `~IOThread`（`io_thread.cpp:98`） | 析构只打印日志，`close(_epoll_fd)`、`close(_event_fd)`、`free(_event_addr)` 全都没有 | 看代码即可 | 析构里补齐（注意：要在 join 之后） |
| D3 | 🟡 | 多处 | 死代码：`EventLoop::_next_idx`（`event_loop.cpp:7`）、`Session::_send_mtx`（`session.h:89`）、`IOThread::enqueue_new_con`（`io_thread.cpp:111`）、`global.h` 的 `HEAD_ID_LEN`/`HEAD_LEN_LEN` | 全局搜索引用 | 删除，或者按原意补全（`_next_idx` 本意可能是真正的轮询分发） |
| D4 | 🟡 | `deal_enque_tasks`／`loop` | `_send_stage == SENDING` 的两处判断在当前调用结构下**永远不成立**（详见 [04 章附录](04-发送链路：发送队列与部分写.md)） | 阅读代码 + 加日志 | 改成 `!_send_que.empty()` 语义更准确 |
| D5 | ⚪ | `loop()` 顶部（`io_thread.cpp:425`） | 错误分支对**任何** fd 都调 `clear_fd(fd)`。万一 `_event_fd` 报了 `EPOLLERR|EPOLLHUP`，会把 eventfd 关掉 → 之后所有跨线程唤醒失效 | 极难自然复现 | 该分支前先判断 `fd == _event_fd`，是则只打日志不关闭 |
| D6 | 🟡 | `read_head_data` 对端关闭处 | `return -1;` 直接写字面量，而不是 `IO_ERROR`（值相同，但语义不统一） | 看代码即可 | 统一用宏 |
| D7 | 🟡 | `Session::Send`（`session.cpp:68`） | 发送侧不校验 `data_len <= 65535`，`htons(data_len)` 会静默截断成一个错误长度；也不校验 `<= BUFF_SIZE` | 传一个 70000 字节的 body 进 `Send` | `if (data_len > 0xFFFF) return;`（或分片） |
| D8 | 🟡 | `Server::run()` accept 处 | 没有处理 `EMFILE`/`ENFILE`（fd 耗尽）：目前只是 `perror` + `break`，之后 listen 事件可能反复触发；也没有连接数上限 | `ulimit -n 32` 后狂连 | 预留一个空闲 fd，`EMFILE` 时先 `close` 它再 `accept` 丢掉连接 |
| D9 | 🟡 | 全局 | 无超时/心跳/空闲回收（`epoll_wait` 超时是 `-1`）、无 `TCP_NODELAY`、无优雅关闭（先发完再 close）、无 backlog 调整 | 连上后不发数据，观察连接永不超时 | 高级改造题（第 8 章） |
| D10 | 🟡 | `~Server` | 退出时不 close 已建立的客户端连接（靠进程退出兜底） | 退出时 `ls -l /proc/<pid>/fd` | 遍历 `_sessions` 逐个 `clear_fd` |
| D11 | 🟡 | 多处 | 编译告警：`for (int i = 0; i < conns.size(); i++)` 有符号/无符号比较；`int remain = HEAD_LEN - size_t` 窄化；`int _event_count` 与 `size_t` 比较 | `-Wall -Wextra` 编译 | 统一用 `size_t` / 显式 `static_cast` |
| D12 | 🟡 | `main.cpp:10` `signal_handler` | 信号处理函数里调用 `std::cout`（不是 async-signal-safe）；`g_server` 是普通指针，理论上存在竞态 | 阅读代码 | handler 里只做 `write()` 之类的异步安全操作，或用 `volatile sig_atomic_t` 打标志、主循环检查 |
| D13 | ⚪ | `defer.h` | `Defer` 析构时调用 `_func()`，若抛异常会导致 `std::terminate`（noexcept 语境） | — | 加 `noexcept` 或禁止 `_func` 抛异常 |
| D14 | ⚪ | `EventLoop` 构造函数 | 先 `thr->start()` 再 `emplace_back`。当前线程不访问容器所以安全，但"对象还没入容器线程就开跑"是危险模式 | 阅读代码 | 先 `emplace_back` 再对 back() 调 `start()` |

## 4. 编译告警（自己复刻时建议一开始就开）

```bash
g++ -std=c++17 -Wall -Wextra -O2 -g -pthread *.cpp -o event_server
```

预计会看到的主要是三类：有符号/无符号比较、`size_t` → `int` 窄化、以及 `_event_fd`/`wakeup()` 里 `write` 返回值未使用（`-Wunused-result`，如果用了 `_FORTIFY_SOURCE`）。

**建议**：复刻时把 `-Wall -Wextra -Werror` 开着写。这份项目里的多数"小瑕疵"都会在编译期直接暴露出来。
