## 2. 启动时序（原版真实的打印顺序）

`Server` 的构造函数里就创建了 `EventLoop`，而 `EventLoop` 的构造函数里会把所有 IO 线程 **start 起来**。所以"线程已经在跑 epoll 了"发生在 `run()` 之前：此时主线程还没开始 accept，IO 线程已经空转等事件。

```
main()
 ├─ ConfigMgr::Inst().loadFromFile("config.ini")     # 注意：相对当前工作目录！
 ├─ cfg.get<int>("server.port", 12345)               # 打印 "server.port = 12345"
 ├─ Server server(port)
 │    ├─ create_and_bind(port)                       # socket + SO_REUSEADDR + bind + listen
 │    ├─ set_nonblocking(_listen_fd)
 │    ├─ 打印 "server _listen_fd is 3 / _event_fd is 4 / _epoll_fd is 5"
 │    ├─ epoll_ctl(ADD, _listen_fd, EPOLLIN|EPOLLET) # 监听 fd 用 ET
 │    ├─ epoll_ctl(ADD, _event_fd,  EPOLLIN)         # eventfd 用 LT（读完就不可读，安全）
 │    ├─ malloc(_event_addr, 32)
 │    └─ EventLoop(thread_num)                       # 打印 "construt event_loop num is 4"
 │         └─ for i in 0..N-1: IOThread(i) { eventfd; epoll_create1; 注册自己 eventfd }
 │              └─ thr->start()  ← 线程在这里就开跑了
 ├─ g_server = &server
 ├─ signal(SIGINT/SIGTERM, signal_handler)
 └─ server.run()  ← 主线程阻塞在 epoll_wait
```

读代码时请记住这个顺序，它解释了两个现象：

1. 你按 Ctrl-C，主线程 `run()` 退出后，**IO 线程是被 `~Server → StopIOThread → ~EventLoop::join` 收掉的**；
2. `config.ini` 用相对路径打开，所以**在哪个目录启动程序，就必须在哪个目录放 `config.ini`**（放到 `build/` 里忘记拷，就会看到 `Failed to load config.ini`）。

## 3. 线程模型

### 3.1 有几个线程

`1 (主线程) + N (IOThread, 由 config.ini 的 thread_num 决定)`。默认配置是 4。

主线程 = **acceptor**：只做 `accept` 和分发，不碰任何客户端数据。
IO 线程 = **Reactor**：每个线程独立 `epoll_wait`，处理分配给自己的所有连接的读写。

这就是经典的 **one loop per thread**（muduo 的核心结构）：线程之间除了"投递任务 + 唤醒"之外，没有共享数据。

### 3.2 连接怎么分给线程

`event_loop.cpp:39`：

```cpp
for (int i = 0; i < conns.size(); i++) {
    auto fd = conns[i];
    auto index = fd % _work_threads.size();   // 用 fd 取模
    _work_threads[index]->catche_new_con(fd);
    notify_threads.insert(index);
}
for (auto index : notify_threads) _work_threads[index]->wakeup();  // 每个线程只唤醒一次
```

两个细节值得学：

- **不是轮询，是按 fd 取模**。因为 fd 是内核递增分配并复用的，取模天然比"轮询计数"更稳定：同一个 fd 永远落在同一个线程，避免"连接迁移"带来的状态混乱。
- `notify_threads` 是 `std::set`：一批新连接如果分到同一个线程，**只写一次 eventfd**。这是"批量唤醒"的写法，防止 accept 1000 个连接就写 1000 次 eventfd。

顺带一提：`EventLoop` 里那个 `std::atomic<size_t> _next_idx`（`event_loop.cpp:7` 初始化为 0）**从来没被用过**，是死代码——原意大概是想做真正的轮询分发。这是一个很好的"批判性阅读"练习点。

### 3.3 四条核心不变量（读代码时反复回头确认）

> **不变量 A：一个连接的所有读写，永远只发生在同一个 IO 线程里。**
> 因为 fd 取模是确定性的，且连接建立后不会再迁移。
> → 推论：`Session` 的所有成员（`_recv_stage`、`_head_buf`、`_send_que`…）**都不需要加锁**。这就是 `session.h:89` 那个 `_send_mtx` 注释说"目前不用了"的原因，它也是死代码。

> **不变量 B：跨线程只通过"任务队列 + eventfd"传递意图，不直接碰对方的数据结构。**
> `_tasks` 由 `_task_mtx` 保护（`io_thread.h:75-76`），队列里装的是值语义的 `IOTask`（fd + 类型 + 数据副本）。
> → 推论：任何"别的线程想让我做点事"都必须走 `enqueue_task`，并在入队后 `wakeup()`。

> **不变量 C：所有 socket 都是非阻塞的，且 ET 模式下必须"循环读写到 EAGAIN"。**
> 少读一次，剩下的数据就再也没有事件通知了 → 连接假死。

> **不变量 D：先 `_sessions.erase(fd)`，再 `close(fd)`。**
> `io_thread.cpp:164` 的 `clear_fd` 严格按 `erase → epoll_ctl(DEL) → close` 顺序执行。因为 `close` 之后这个 fd 号可能立刻被 `accept` 复用，如果先 close 再 erase，就会出现"新连接被旧 Session 顶掉"的竞态。这是一个很容易被忽略、但真实存在的正确性细节。

## 4. 一次 echo 的完整数据流（8 个动作）

```
① 客户端 write(4字节头 + body)
② IO 线程 epoll_wait 返回 EPOLLIN
③ read_head_data()  → 拿全 4 字节头，解析出 msg_type / body_len，校验 body_len<=2048
④ read_body_data()  → 读全 body
⑤ Session::Send(body, type) → enqueue_send_data → enqueue_task 入队 + 写 eventfd 唤醒【自己】
⑥ 下一轮 epoll_wait 返回 eventfd 事件 → deal_enque_tasks()
⑦ 取出 SendData 任务 → DataBuf 自动拼上头 → send_data() 直接 write
⑧ 若 write 遇 EAGAIN → 注册 EPOLLOUT；等可写事件来了 → handle_epollout() 续写 → 发完摘掉 EPOLLOUT
```

第 ⑤⑥ 步是本项目一个显眼的"设计痕迹"：**回显本来就在 owner 线程里，完全可以同步发送，却绕了一圈任务队列。** 好处是"所有发送都走同一条路径、逻辑统一"；代价是每个包多一次 eventfd 写 + 一次 epoll 往返。
