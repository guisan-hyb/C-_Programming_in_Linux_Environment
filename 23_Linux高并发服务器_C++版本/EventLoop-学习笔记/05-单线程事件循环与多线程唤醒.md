# 05 · 单线程事件循环与多线程唤醒

对应代码：`io_thread.cpp:425` `IOThread::loop()`、`io_thread.cpp:171` `deal_enque_tasks()`、`io_thread.cpp:126` `wakeup()`、`server.cpp:135` `Server::run()`、`event_loop.cpp:39` `NotifyNewCons()`。

## 1. 骨架：一个 epoll 循环的六件事

任何 Reactor 的循环都是这几步，区别只在细节：

```
loop:
  1. epoll_wait 等事件（阻塞）
  2. 处理错误事件（EPOLLERR/EPOLLHUP）
  3. 处理"控制面"事件（这里是 eventfd：有新任务要处理）
  4. 处理"数据面"事件（读/写）
  5. 循环直到 _stop
  6. 退出收尾
```

`IOThread::loop()` 的完整流程（可直接对照你手上那张《C++改造架构》图）：

```
                    ┌──────────────────────────────┐
                    │  epoll_wait(_epoll_fd, -1)   │
                    └──────────────┬───────────────┘
                                   │ nfds
              ┌────────────────────┼─────────────────────┐
              ▼                    ▼                     ▼
        nfds < 0            nfds == _event_count      遍历 nfds 个事件
     EINTR → continue      且未扩容过 → realloc 双倍         │
     其他 → break                                          │
                                                           ▼
                                ┌──────────────────────────────────────┐
                                │ events & (EPOLLERR|EPOLLHUP)?        │
                                │   → getsockopt(SO_ERROR) 打印        │
                                │   → clear_fd(fd) 继续下一个           │
                                └──────────────┬───────────────────────┘
                                               ▼
                                ┌──────────────────────────────────────┐
                                │ fd == _event_fd ?                    │
                                │   → read(eventfd) 清空计数            │
                                │   → deal_enque_tasks()               │
                                │     返回 false(收到 Shutdown) → return│
                                └──────────────┬───────────────────────┘
                                               ▼
                                ┌──────────────────────────────────────┐
                                │ events & (EPOLLIN|EPOLLOUT)?         │
                                │   在 _sessions 里找 fd，找不到就跳过   │
                                │   EPOLLIN  → 读循环直到 EAGAIN        │
                                │   EPOLLOUT → handle_epollout() 续写   │
                                └──────────────────────────────────────┘
```

代码里的几个细节：

```cpp
int nfds = epoll_wait(_epoll_fd, _event_addr, _event_count, -1);   // -1 = 永久阻塞
if (nfds < 0) {
    if (errno == EINTR) continue;     // 被信号打断是正常现象，重试即可
    perror("epoll_wait"); break;
}
if ((size_t)nfds == _event_count && !_expanded_once) {   // 事件数组满了 → 扩容一次
    size_t new_count = _event_count * 2;
    struct epoll_event *new_addr = (struct epoll_event *)realloc(_event_addr, sizeof(struct epoll_event) * new_count);
    if (new_addr) { _event_addr = new_addr; _event_count = new_count; }
    _expanded_once = true;                                // 只允许扩一次（1024 → 2048）
}
```

- `timeout = -1`：**没有超时机制**。所以这份代码做不了心跳/空闲连接回收/定时任务 —— 想做的话要把 `-1` 改成"最近一个定时器的时间差"。这是它离"生产可用"最远的一块，第 8 章的进阶题会让你补上。
- `_expanded_once` 是个一次性开关：只扩一次，之后即使又满了也只在下一轮继续处理。够用（超出的 fd 会在下次 `epoll_wait` 再返回），但不算优雅。
- `EPOLLERR|EPOLLHUP` 这两个事件**不需要注册**，内核会自动上报，所以必须处理，否则会出现"连接已断但你以为还活着"。

## 2. 控制面：为什么必须有 eventfd

### 2.1 问题

主线程 accept 到新连接，想交给 IO 线程。但 IO 线程此刻**正阻塞在 `epoll_wait` 里**。你往一个 `std::queue` 里 `push` 一个任务，IO 线程根本不知道——它要等到"某个网络事件恰好发生"才会醒来，如果这个连接一直不发数据，任务就永远躺着。

### 2.2 解法：让"有任务了"这件事变成一个 fd 事件

`eventfd` 是 Linux 提供的**计数器型 fd**：

| 操作 | 效果 |
| --- | --- |
| `eventfd(0, EFD_NONBLOCK)` | 创建一个计数器，初值 0，非阻塞 |
| `write(fd, &one, 8)` | 计数器 += 1（本项目的 `wakeup()`，`io_thread.cpp:126`） |
| `read(fd, &cnt, 8)` | 返回当前计数值并**清零**；计数为 0 时非阻塞返回 `EAGAIN` |
| 计数器 > 0 | 该 fd **可读** → 注册在 epoll 上就能收到 `EPOLLIN` |

于是：

```
主线程                                   IO 线程
  │ 加锁 push 任务到 _tasks                │ 阻塞在 epoll_wait
  │ write(eventfd, 1)  ────────────────►  │ epoll_wait 返回，fd == _event_fd
  │                                        │ read(eventfd) 清空计数
  │                                        │ deal_enque_tasks() 取任务执行
```

**为什么不用条件变量？** 可以，但那样 IO 线程就得在"等 epoll"和"等条件变量"之间二选一（除非再引入信号或额外线程）。把"通知"统一成 fd 事件之后，**整个线程只有一个阻塞点（epoll_wait）**，代码简单得多。这就是 muduo 用 `eventfd`、libevent 用 `socketpair`、Go runtime 用 `netpoll` 的同一套思路。

### 2.3 两个构造细节

构造函数里（`io_thread.cpp:5`）依次做了：

```
_event_fd = eventfd(0, EFD_NONBLOCK)
_epoll_fd = epoll_create1(0)
add_fd(_event_fd, EPOLLIN)                       ← eventfd 只注册 EPOLLIN，没有 EPOLLET
_event_addr = malloc(sizeof(epoll_event) * 1024) ← 事件数组初始 1024
```

1. **eventfd 用 LT（不加 EPOLLET）是安全的**：因为 `read` 一次就把计数清零，"可读"状态随即消失，不会反复通知。
2. **成员初始化列表里 `_stop(true)`**：`start()` 里才置 `false` 并创建线程。这保证"线程还没启动时调用 stop 也不会出问题"。

## 3. `deal_enque_tasks()`：任务队列的消费（`io_thread.cpp:171`）

```cpp
bool IOThread::deal_enque_tasks() {
    std::queue<std::shared_ptr<IOTask>> q;
    { std::lock_guard<std::mutex> lk(_task_mtx); std::swap(q, _tasks); }   // ★ 整体换出

    while (!q.empty()) {
        auto task = q.front(); q.pop();

        if (task->_type == TaskType::RegisterConn) {
            auto sess = std::make_shared<Session>(task->_fd, this);
            _sessions[task->_fd] = sess;
            set_nonblocking(task->_fd);                    // ★ 先设非阻塞
            add_fd(task->_fd, EPOLLIN | EPOLLET);          // ★ 再注册 epoll（顺序不能反！）
            continue;
        }
        if (task->_type == TaskType::SendData) { /* 见第 4 章 */ }
        if (task->_type == TaskType::Shutdown) return false;   // 让 loop() 退出
    }
    return true;
}
```

三处值得学：

- **`swap` 换出整个队列，而不是在锁里逐个处理**：互斥锁只持有几纳秒。这样生产者在消费过程中可以继续 `push`（那些任务会等下一轮 eventfd），锁竞争降到最低。这是"把临界区缩到最小"的教科书写法。
- **`set_nonblocking` 必须在 `add_fd` 之前**：如果先注册进 epoll（ET）再设非阻塞，中间万一有数据到达，你可能用阻塞 `read` 卡死整个 IO 线程。顺序错了就是"偶发卡死"的经典 bug。
- **RegisterConn 是"连接初始化"的唯一入口**：连接的创建、非阻塞设置、epoll 注册全部集中在 owner 线程里做，其他线程只传一个 fd 数字。这样连"连接对象"本身都不需要跨线程同步。

## 4. 主线程：accept 与分发（`server.cpp:135`）

```cpp
void Server::run() {
    _stop = false;
    while (!_stop) {
        int nfds = epoll_wait(_epoll_fd, _event_addr, _event_count, -1);
        ...
        for (int i = 0; i < nfds; i++) {
            int fd = _event_addr[i].data.fd;
            uint32_t evs = _event_addr[i].events;
            if (evs & (EPOLLERR | EPOLLHUP)) { /* getsockopt 打印，continue */ }

            if (fd == _listen_fd) {
                struct sockaddr_in cli; socklen_t len = sizeof(cli);
                while (1) {                                  // ★ ET：必须循环 accept 到 EAGAIN
                    int conn_fd = accept(_listen_fd, (struct sockaddr*)&cli, &len);
                    if (conn_fd < 0) {
                        if (errno == EAGAIN || errno == EWOULDBLOCK) break;
                        if (errno == EINTR) continue;
                        perror("accept"); break;
                    }
                    _con_fds.push_back(conn_fd);
                    printf("Accepted fd=%d\n", conn_fd);
                }
                if (!_con_fds.empty()) { _loop->NotifyNewCons(_con_fds); _con_fds.clear(); }
                continue;
            }
            if (fd == _event_fd) { read(_event_fd, &cnt, 8); return; }   // stop() 触发的退出
        }
    }
}
```

要点：

- **`listen_fd` 也是 `EPOLLIN|EPOLLET`**，所以 accept 必须循环到 `EAGAIN`。道理和读数据一样：一次事件可能对应多个已完成三次握手的连接，只 accept 一个就会把剩下的"漏到下次"（ET 下甚至可能长时间不通知）。这是"漏 accept"的常见坑。
- **一个 epoll 实例只被一个线程 `epoll_wait`（主线程）**，所以 accept 不会有惊群问题。这份代码的多线程是"主 Reactor 接受 + N 个子 Reactor 处理"，而不是"N 个线程抢 accept"。
- `socklen_t len = sizeof(cli)` 声明在循环外：IPv4 场景下没问题，但如果以后改成 `sockaddr_storage` 同时支持 IPv6，**必须每轮重置 `len`**，否则第二次 accept 可能失败。
- accept 出来的 fd **此时还是阻塞的**，真正设非阻塞是在 IO 线程的 `RegisterConn` 里（见上一节）。中间这段时间没人读它，所以安全；但这个"两段式"顺序值得记住。

## 5. 分发与唤醒（`event_loop.cpp:39`）

```cpp
void EventLoop::NotifyNewCons(std::vector<int> &conns) {
    std::set<int> notify_threads;
    for (int i = 0; i < conns.size(); i++) {
        auto fd = conns[i];
        auto index = fd % _work_threads.size();      // 确定性分发
        _work_threads[index]->catche_new_con(fd);    // 只入队
        notify_threads.insert(index);
    }
    for (auto index : notify_threads) _work_threads[index]->wakeup();   // 每个线程唤醒一次
}
```

注意这里用了两个不同的入队函数：

| 函数 | 行为 | 用在哪 |
| --- | --- | --- |
| `catche_new_con(fd)`（`io_thread.cpp:117`） | **只**加锁入队，不唤醒 | 批量分发时 |
| `enqueue_task(task)`（`io_thread.cpp:149`） | 加锁入队 + `wakeup()` | 通用（含 `enqueue_new_con`、`stop`） |

批量场景下先连续入队、最后统一唤醒，等价于"**合并通知**"：1000 个新连接若落到同一个线程，只写 1 次 eventfd。这类"批处理 + 合并唤醒"的思路在高性能服务器里到处都是（比如日志的 group commit）。

顺带说：`enqueue_new_con()`（`io_thread.cpp:111`）从来没被调用过，是死代码；`catche_new_con` 名字里的 "catche" 也是拼写笔误（应为 catch）。

## 6. 全局视角：一次"新连接 → 回显 → 关闭"的完整时间线

```
客户端           主线程                      IO线程#k                 内核
  │  connect ──►  EPOLLIN(listen_fd)
  │              accept() 循环到 EAGAIN
  │              _con_fds=[7] → NotifyNewCons
  │              enqueue RegisterConn(7) + write(eventfd)
  │                                          ◄── eventfd 可读
  │                                          deal_enque_tasks()
  │                                            new Session(7)
  │                                            set_nonblocking(7)
  │                                            epoll_ctl(ADD,7,EPOLLIN|EPOLLET)
  │  write(包) ─────────────────────────────► EPOLLIN(7)
  │                                          read 循环 → 拆包 → 完整包
  │                                          Session::Send → enqueue SendData(7) + eventfd
  │                                          ◄── eventfd 可读 → send_data() write()
  │  ◄───────────────────────────── 收到回显
  │  close ────────────────────────────────► EPOLLIN(7) → read 返回 0
  │                                          clear_fd(7): erase+DEL+close
```
