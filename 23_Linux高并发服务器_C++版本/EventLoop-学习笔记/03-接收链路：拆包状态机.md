# 03 · 接收链路：拆包状态机

对应代码：`io_thread.cpp:238` `read_head_data()`、`io_thread.cpp:313` `read_body_data()`，调用方是 `io_thread.cpp:425` `loop()` 的 `EPOLLIN` 分支。

## 1. 为什么需要一个状态机

TCP 提供的是**字节流**，不是"消息流"。你发的 4 个字节，对端可能一次 `read` 拿到，也可能分 3 次拿到；你的两个包，可能被合并成一次 `read` 交付。所以应用层必须自己干三件事：

1. **划边界**：先读固定长度的头，从头里拿 `body_len`；
2. **记进度**：头/体都可能只读到一半，必须记住"已经攒了多少字节"；
3. **可重入**：下次事件来了，从上次断掉的位置继续，而不是重头再读。

本项目的实现方式：`_recv_stage`（阶段） + `HeadBuf._offset`（头进度） + `DataBuf._offset`（体进度）三个变量联合表达状态。

## 2. `read_head_data()` 逐分支讲解

```cpp
int IOThread::read_head_data(std::shared_ptr<Session> sess)
{
    if (sess == nullptr) return -1;
    int remain = HEAD_LEN - sess->_head_buf->_offset;              // ← 还要读几字节
    ssize_t read_len = read(sess->_fd,
                            sess->_head_buf->_buf + sess->_head_buf->_offset,
                            remain);                               // ← 续写到正确偏移
    ...
}
```

**两个要点**：

- `remain` 是"还缺多少"，不是"要读多少"；续读时必须写到 `_buf + _offset`，不能写回 `_buf`；
- `!read` 的返回值必须区分 4 种情况，这是非阻塞 IO 的基本功。

| `read` 结果 | 含义 | 代码动作 | 返回 |
| --- | --- | --- | --- |
| `> 0` 且 `< remain` | 只读到半个头 | `_recv_stage = HEAD_RECVING`；`_offset += read_len` | `IO_CONTINUE(2)` → 外层继续循环再读一次 |
| `> 0` 且 `== remain` | 头读全了 | 解析 `type`/`len`；校验 `body_len <= BUFF_SIZE`；`_recv_stage = BODY_RECVING`；`_data_buf = make_shared<DataBuf>(type, len)`；`_offset += read_len` | `IO_CONTINUE(2)` |
| `< 0`，`errno==EAGAIN/EWOULDBLOCK` | 内核缓冲已读空 | **什么都不改，保持状态** | `IO_EAGAIN(1)` → 外层 `break`，回去 `epoll_wait` |
| `< 0`，`errno==EINTR` | 被信号打断，不是错误 | 无 | `IO_CONTINUE(2)` → 立刻重试 `read` |
| `< 0`，其他 `errno` | 真错误（ECONNRESET 等） | `perror` | `IO_ERROR(-1)` → 外层 `clear_fd` |
| `== 0` | 对端正常关闭（FIN） | 打印 `read peer closed` | 直接 `return -1`（值等于 `IO_ERROR`，但没走宏，风格不统一） |

解析头的代码（`io_thread.cpp` 中段）：

```cpp
uint8_t *hdr = (uint8_t *)(sess->_head_buf->_buf);
uint16_t t, l;
memcpy(&t, hdr,     sizeof(t));      // 用 memcpy 而不是指针强转：避免未对齐访问 + 严格别名问题
memcpy(&l, hdr + 2, sizeof(l));
uint16_t msg_type = ntohs(t);        // 网络序 → 主机序
uint16_t body_len = ntohs(l);

if (body_len > BUFF_SIZE) {          // ★ 长度校验：不校验就是内存/协议攻击面
    std::cout << "msg body too big" << std::endl;
    return IO_ERROR;
}
sess->_recv_stage = BODY_RECVING;
sess->_head_buf->_offset += read_len;          // = HEAD_LEN
sess->_data_buf = std::make_shared<DataBuf>(msg_type, body_len);
return IO_CONTINUE;
```

值得单独记住的两点：

1. **`memcpy` 而不是 `*(uint16_t*)hdr`**：`hdr` 是 `char*`，强转解引用在未对齐地址上是 UB（x86 侥幸能跑，ARM 上直接崩）。这里用 `memcpy` 是正确写法。
2. **`body_len > BUFF_SIZE` 的校验是必须的**：否则对端谎报 60000 字节，你就得分配 60KB；谎报得更大就是内存耗尽。**"对端给的任何长度字段都不能信"** —— 这是协议实现的第一条铁律。

顺带一个**真实缺陷**：`body_len == 0` 没有被特判，会被当成正常包进入 `BODY_RECVING`，然后 `read_body_data` 里 `remain = 0` 执行 `read(fd, buf, 0)`，`read` **返回 0**，而代码把 `0` 解释为"对端关闭" → **发一个空包 body 就会被踢下线**。复现方法和修法见 [06 章](06-生命周期、错误处理与已知缺陷.md#3-已知缺陷清单)。

## 3. `read_body_data()` 逐分支讲解

```cpp
int remain = sess->_data_buf->_data_len - sess->_data_buf->_offset;
ssize_t read_len = read(sess->_fd,
                        sess->_data_buf->_buf + sess->_data_buf->_offset,
                        remain);
```

| `read` 结果 | 代码动作 | 返回 |
| --- | --- | --- |
| `> 0` 且 `< remain` | `_offset += read_len` | `IO_CONTINUE(2)` → 继续等剩余字节 |
| `> 0` 且 `== remain` | ① `_offset += read_len` ② **业务：`sess->Send(str, type)` 回显** ③ `_data_buf = NULL` ④ `_recv_stage = NO_RECV` ⑤ `memset(_head_buf->_buf, 0, HEAD_LEN)` ⑥ `_head_buf->_offset = 0` | `IO_CONTINUE(2)` → 立刻尝试解析"粘在后面的下一个包" |
| `== 0` | 对端关闭 | `IO_ERROR(-1)` |
| `< 0` `EINTR` | — | `IO_CONTINUE(2)` |
| `< 0` `EAGAIN` | — | `IO_EAGAIN(1)` |
| `< 0` 其他 | `perror` | `IO_ERROR(-1)` |

**收完一个包后那 4 行复位（③④⑤⑥）是整段代码里最容易漏、后果最严重的部分**：

- 忘了 `_data_buf = NULL` → 内存只增不减；
- 忘了 `_recv_stage = NO_RECV` → 下一个包会被当成"继续读上一个包的体"，状态直接错位；
- 忘了 `_head_buf->_offset = 0` → 下次读头只剩 0 字节可写，`read(fd, buf+4, 0)` 又返回 0，被当成对端关闭 → 连接断。

**自己复刻时，建议专门为这 4 行写一个 `reset_recv_state()` 函数**，让"状态复位"成为一个显式动作，而不是散落的赋值。

## 4. 粘包与半包：把时序画出来

### 4.1 粘包（一次 write 两个包 / 一次 read 两个包）

```
客户端:  write([H1][B1][H2][B2])           # 一次系统调用
内核:    ──── 合并成一段字节流 ────►
服务端:  read 一次可能拿到 [H1][B1][H2][B2]
         read_head_data → 解析 H1 → BODY_RECVING
         read_body_data → 读全 B1 → 回显 B1 → 复位 → 返回 IO_CONTINUE
         外层 while 继续 → read_head_data → 解析 H2（数据还在内核缓冲里，不需要新事件！）
         read_body_data → 读全 B2 → 回显 B2 → 复位
         再读一次 → EAGAIN → break
```

**关键点**：一次 `EPOLLIN` 可能对应 0 个、1 个、多个完整包。"读到 EAGAIN 才停"既是为了 ET 不丢数据，也是为了把内核缓冲里的多个包一次处理干净。

### 4.2 半包（一个包分两次 write）

```
客户端:  write([H1])            # 只发了头
服务端:  read 拿到 4 字节 → 头完整 → BODY_RECVING，_data_buf 已分配
         read 再读 → EAGAIN → break（回到 epoll_wait 等）

客户端:  write([B1])            # 200ms 之后才发包体
服务端:  EPOLLIN → 状态是 BODY_RECVING → 直接读体 → 补齐 → 回显
```

还有一个更刁钻的情况：**半个头**。

```
客户端:  write([H1 的前 2 字节])
服务端:  read 拿到 2 字节 → read_len(2) < remain(4) → HEAD_RECVING，_offset=2
         read 再读 → EAGAIN → break
客户端:  write([H1 的后 2 字节 + B1])
服务端:  read 从 _buf+2 写入 2 字节补齐头 → 头完整 → 继续读体
```

这三种情况（粘包/半包/半截头）**必须都能通过**，才算真正跑通了接收链路。第 7 章给了对应的验收客户端。

## 5. ET 模式下为什么必须"读到 EAGAIN"

对比一下 LT 和 ET：

| | 触发条件 | 若不读完会怎样 |
| --- | --- | --- |
| LT（水平触发） | 只要**还有数据**就一直通知你 | 下次 `epoll_wait` 还会返回 EPOLLIN，重复通知，浪费 CPU 但不丢数据 |
| ET（边沿触发） | 只在**状态变化**时通知一次（无数据 → 有数据，或又来了新数据） | **剩余的旧数据可能永远不再通知** → 连接假死、丢包，直到对端再发新数据才"醒过来" |

所以 ET 的规则是：**收到一次 EPOLLIN，就要一直读到 `EAGAIN`**。本项目的 `loop()` 用 `while(1)` + `IO_EAGAIN` 才 `break` 就是在遵守这条规则：

```cpp
if (evs & EPOLLIN) {
    while (1) {
        if (_recv_stage == NO_RECV || _recv_stage == HEAD_RECVING) {
            int head_res = read_head_data(sess);
            if (head_res == IO_CONTINUE)  continue;   // 继续读（可能是半截头、也可能是下一个包）
            if (head_res == IO_ERROR)   { clear_fd(fd); break; }
            if (head_res == IO_EAGAIN)  { break; }    // ★ 只有这里能跳出
            continue;
        }
        if (_recv_stage == BODY_RECVING) {
            int body_res = read_body_data(sess);
            if (body_res == IO_CONTINUE) continue;
            if (body_res == IO_ERROR)   { clear_fd(fd); break; }
            if (body_res == IO_EAGAIN)  { break; }
            continue;
        }
    }
}
```

注意返回码设计：`IO_CONTINUE(2)` = "状态有进展，赶紧再试一次"；`IO_EAGAIN(1)` = "内核没数据了，出去等事件"。两个值都由 `global.h` 定义，是整套 IO 代码的"控制信号"。**复刻时建议沿用这套返回码语义，它把"读到一半"和"读空了"区分得很干净。**
