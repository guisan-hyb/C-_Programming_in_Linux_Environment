# 04 · 发送链路：发送队列与部分写

对应代码：`io_thread.cpp:171` `deal_enque_tasks()` 的 `SendData` 分支、`session.cpp:76` `Session::send_data()`、`io_thread.cpp:368` `handle_epollout()`。

## 1. 为什么发送比接收更容易写错

接收是"有数据就一定能读"（读不动就 EAGAIN，等下次事件）；发送则是"**任何时刻都可能写不进去**"：

- 非阻塞 socket 的内核发送缓冲区满了 → `write` 返回 `-1` 且 `errno==EAGAIN`；
- 你只能写进去一部分（部分写），剩下的必须留着；
- 什么时候能继续写？**只能等内核通知你**（EPOLLOUT）。

所以发送必须回答三个问题：

1. 没发完的数据存哪？→ `Session::_send_que` 队列
2. 剩多少没发？→ 每个 `DataBuf` 的 `_offset`
3. 什么时候回来续写？→ 注册 `EPOLLOUT`，收到事件后 `handle_epollout()`

## 2. 两条发送路径

```
有人要发数据（本项目的触发点是"收到一个完整包，要回显"）
        │
        ▼
Session::Send(data, type)                 session.cpp:68
        │  只是投递任务，不做 IO → 天然线程安全
        ▼
Session::_p_ownerthread->enqueue_send_data(fd, msg, type)
        │  加锁入队 + write(eventfd) 唤醒 owner 线程   io_thread.cpp:149/158
        ▼
【owner 线程】deal_enque_tasks() 取出 SendData 任务   io_thread.cpp:171
        │
        ├─ 找不到 fd 的 Session → 直接丢弃（连接已关闭）
        ├─ make_shared<DataBuf>(msgtype, data, size)    ← 这里自动拼上 4 字节头
        │
        ├─ 路径 A：现在能写 → Session::send_data() 立即写
        │        ├─ 全部写完 → 返回 IO_SUCCESS(0)，结束
        │        ├─ 写不动 EAGAIN → 返回 IO_EAGAIN(1) → mod_fd(EPOLLET|EPOLLIN|EPOLLOUT)
        │        └─ 出错 → 返回 IO_ERROR(-1) → erase + epoll_ctl(DEL) + close
        │
        └─ 路径 B：EPOLLOUT 事件来了 → handle_epollout() 从队首续写
                 └─ 队列发空 → epoll_ctl(MOD) 摘掉 EPOLLOUT，回到只监听 EPOLLIN|EPOLLET
```

## 3. `Session::send_data()` 逐行讲解（`session.cpp:76`）

```cpp
int Session::send_data(std::shared_ptr<DataBuf> data) {
    _send_stage = SENDING;
    Defer defer([this]() { this->_send_stage = NO_SEND; });   // ① 出作用域必然复位

    _send_que.push(data);                                      // ② 先入队，再尝试发
    while (!_send_que.empty()) {
        auto send_node = _send_que.front();
        while (send_node->_offset < send_node->_data_len) {     // ③ 从上次断点续写
            auto result = write(_fd,
                                send_node->_buf + send_node->_offset,
                                send_node->_data_len - send_node->_offset);
            if (result > 0) { send_node->_offset += result; continue; }
            if (result < 0) {
                if (errno == EAGAIN || errno == EWOULDBLOCK) return IO_EAGAIN;  // ④ 队列原地保留
                if (errno == EINTR) continue;
                perror("send failed: "); return IO_ERROR;                        // ⑤ 真错误
            }
            if (result == 0) { /* 对端关闭 */ return IO_ERROR; }                 // ⑥
        }
        if (send_node->_offset == send_node->_data_len) { _send_que.pop(); continue; }
    }
    return IO_SUCCESS;                                          // ⑦ 队列空了才算成功
}
```

六个关键点：

- **① `Defer` 复位 `_send_stage`**：这是给"同一线程内的并发逻辑"用的标志位。写函数是可能提前 `return` 的（EAGAIN / 错误），如果手动在每个 `return` 前复位，迟早漏一个；用 RAII 就永远不会漏。这就是 `defer.h` 存在的意义（等价于 Go 的 `defer`、Rust 的 `Drop`）。
- **② "先入队再发"**：即使立刻就能写完，数据也先进队列。好处是"待发数据永远只有一个地方可查"，不会出现"有的在栈上、有的在队列里"。代价是多一次 `push/pop`（可以忽略）。
- **③ 从 `_offset` 续写**：这就是"部分写"的核心。上次写到 700 字节，这次从 `_buf+700` 继续。
- **④ `return IO_EAGAIN` 时绝对不能在队列里丢掉这个节点**：它带着 `_offset`，是下次续写的唯一依据。
- **⑤⑥ 出错/对端关闭**：返回 `IO_ERROR`，由调用方 `deal_enque_tasks` 负责 `erase + epoll_ctl(DEL) + close`。**"IO 函数不负责清理连接，只负责报告状态"** 这个分工很清晰，值得学。
- **⑦ 返回 `IO_SUCCESS` 时队列一定为空**，所以"队列非空" = "还有数据等着写" = "EPOLLOUT 必须保持订阅"。

调用方（`io_thread.cpp` 的 `SendData` 分支）：

```cpp
auto send_res = iter->second->send_data(data_buf);
if (send_res == -1) {                       // IO_ERROR
    _sessions.erase(task->_fd); del_fd(task->_fd); close(task->_fd); continue;
}
if (send_res == 1) {                        // IO_EAGAIN
    mod_fd(task->_fd, EPOLLET | EPOLLIN | EPOLLOUT);   // ★ 订阅"可写"
    continue;
}
continue;                                   // IO_SUCCESS
```

## 4. `handle_epollout()` 逐行讲解（`io_thread.cpp:368`）

```cpp
void IOThread::handle_epollout(std::shared_ptr<Session> sess) {
    sess->_send_stage = SENDING;
    Defer defer([sess]() { sess->_send_stage = NO_SEND; });   // ★ 按值捕获 shared_ptr！

    while (!sess->_send_que.empty()) {
        auto send_data = sess->_send_que.front();
        while (send_data->_offset < send_data->_data_len) {
            auto write_len = write(sess->_fd, send_data->_buf + send_data->_offset,
                                   send_data->_data_len - send_data->_offset);
            if (write_len > 0) { send_data->_offset += write_len; continue; }
            if (write_len < 0) {
                if (errno == EAGAIN || errno == EWOULDBLOCK) return;  // ★ 保留 EPOLLOUT，直接走人
                if (errno == EINTR) continue;
                clear_fd(sess->_fd); return;                          // 真错误 → 关连接
            }
            clear_fd(sess->_fd); return;                              // write 返回 0：对端关闭
        }
        sess->_send_que.pop();                                        // 这个包发完了
    }

    // 队列清空：摘掉 EPOLLOUT
    struct epoll_event ev;
    ev.events = EPOLLIN | EPOLLET;
    ev.data.fd = sess->_fd;
    epoll_ctl(_epoll_fd, EPOLL_CTL_MOD, sess->_fd, &ev);
}
```

### 4.1 `Defer defer([sess](){...})` 为什么用按值捕获 `shared_ptr`

这一行是全项目最"值钱"的细节之一。想一想 `clear_fd(sess->_fd)` 做了什么：

```cpp
void IOThread::clear_fd(int fd) { _sessions.erase(fd); del_fd(fd); close(fd); }
```

`_sessions.erase(fd)` 会把 map 里那个 `shared_ptr<Session>` 销毁 —— 如果**没有别的持有者**，`Session` 对象当场被析构。而此时我们还在 `handle_epollout` 里用着 `sess`（函数参数 + `Defer` 捕获）！

`Defer` 按值捕获了一份 `shared_ptr`，加上函数参数的引用，引用计数 ≥ 2，所以对象在这个函数彻底返回之前**一定活着**，"用完再销毁"是安全的。如果这里写成 `Defer defer([&sess](){...})` 或捕获裸指针，就会变成 use-after-free（在 ASAN 下会直接报错）。

> **一句话结论**：只要某个函数要在执行过程中"可能把对象从容器里删掉"，就必须在函数作用域内持有一份 `shared_ptr`。

### 4.2 为什么 EPOLLOUT 必须"用完就摘"

```cpp
ev.events = EPOLLIN | EPOLLET;      // 只保留读，去掉 EPOLLOUT
epoll_ctl(_epoll_fd, EPOLL_CTL_MOD, sess->_fd, &ev);
```

如果发完之后**不摘掉 EPOLLOUT**：

- **LT 模式**：socket 只要可写（绝大多数时间都可写），`epoll_wait` 就会一直返回 EPOLLOUT → `handle_epollout` 一直空转 → **单核 100% CPU**。这就是"按需订阅 EPOLLOUT"这条规矩的来源（muduo 里也是这套做法）。
- **ET 模式**：不会持续空转（只有"从不可写变可写"才触发一次），但每次 `epoll_ctl(MOD)` 都会让内核重新检查就绪状态并可能立刻返回一次事件，日志上会看到莫名其妙的 EPOLLOUT，掩盖真正的逻辑问题。

所以正确的姿势是：**需要时 `MOD` 加上 EPOLLOUT，队列发空后 `MOD` 去掉 EPOLLOUT**。本项目的 `mod_fd` / 结尾的 `epoll_ctl` 正好构成这一对。

> 小吐槽：结尾这段本可以直接调用现成的 `mod_fd(sess->_fd, EPOLLIN | EPOLLET)`，却手写了一遍 `epoll_event`（代码重复）。复刻时建议统一走 `mod_fd`。

### 4.3 `write` 返回 0 也要当成错误

`write` 返回 0 在 socket 上意味着"什么都没写进去"，通常等于对端已经关闭。当成错误处理并关连接是对的，**千万不要写成 `while(write(...) > 0)` 这种一旦返回 0 就静默退出的循环**。

## 5. 完整发送状态图

```
                    ┌──────────────┐
     Send(data) ───►│  _send_que   │  队列里可能有【多个】待发包
                    └──────┬───────┘
                           │ 尝试写
                           ▼
                 ┌───────────────────┐
                 │  write() 全部成功  │──► 队列空，返回 IO_SUCCESS
                 └─────────┬─────────┘
                           │ write() 返回 EAGAIN（内核发送缓冲满）
                           ▼
              ┌────────────────────────────┐
              │ mod_fd(EPOLLIN|EPOLLOUT|ET)│   ← 告诉内核"可写了叫我"
              └──────────────┬─────────────┘
                             │  内核发送缓冲腾空 → EPOLLOUT 事件
                             ▼
              handle_epollout(): 从队首 _offset 处续写
                             │
              ┌──────────────┴──────────────┐
              ▼                             ▼
        又满了(EAGAIN) → 直接 return     队列发空 → MOD 摘掉 EPOLLOUT
        （EPOLLOUT 保持订阅，等下次）      （回到纯 EPOLLIN + ET）
```

## 6. 怎么把 EPOLLOUT 这条路径真的跑起来

包的 body 上限只有 2048 字节，正常本地回环测试**几乎不可能**把内核发送缓冲写满。要触发 EAGAIN，得制造"服务端写得比客户端读得快"的场面：

1. 客户端把 `SO_RCVBUF` 设小（如 2KB）；
2. 客户端**连续发送大量包，但一个字节都不读**；
3. 服务端不停 echo，发送缓冲很快填满 → `write` 返回 EAGAIN → 进入 EPOLLOUT 路径；
4. 观察：服务端 CPU 不飙、日志正常；如果哪一步写错了（比如忘了在 EPOLLOUT 里续写），客户端就会**卡住收不到数据**或**连接被断开**。

`echo_client.py` 的 `flood` 模式就是干这个的，见 [07 章](07-在Linux虚拟机上跑通与联调.md)。

想直接看到 EPOLLOUT 分支被走到，可以在 `handle_epollout()` 开头加一行 `fprintf(stderr, "epollout fd=%d que=%zu\n", sess->_fd, sess->_send_que.size());`，跑完再把日志删掉。

## 附录：那个"反直觉的"死分支

`io_thread.cpp` 里有两处判断 `_send_stage == SENDING`：

```cpp
// deal_enque_tasks 里
if (iter->second->_send_stage == SENDING) { iter->second->enqueue_data(data_buf); continue; }

// loop() 的 EPOLLOUT 分支里
if (sess->_send_stage == SENDING) continue;
```

但 `_send_stage` 只在 `Session::send_data` 和 `handle_epollout` 内部被置为 `SENDING`，而这两个函数都用了 `Defer`，**离开作用域就复位成 `NO_SEND`**；而这两处判断都发生在函数之外（`deal_enque_tasks` 和 `loop`）。所以它们**在当前调用结构下永远不成立**，属于防御性死代码。

它想表达的真实语义是"**这个连接还有数据没发完**"，而正确的判断依据应该是 `!_send_que.empty()`（或者"是否注册了 EPOLLOUT"）。复刻时你可以把这两处换成队列判断，语义更准确 —— 这也是一道很好的"批判性阅读"题。
