根据你提供的目录结构，你的项目分为 `server` 和 `client` 两个独立的模块。其中 `server` 模块包含头文件和多个源文件，`client` 模块有两个独立的测试文件。

既然 `CMakePresets.json` 你已经配置好了，下面是你应该使用的 `CMakeLists.txt` 完整写法。我为你增加了**警告提示**和**文件组织**的最佳实践：

### `CMakeLists.txt`

```cmake
cmake_minimum_required(VERSION 3.20)
project(EPollHighPerfServer C)

set(CMAKE_C_STANDARD 11)
set(CMAKE_C_STANDARD_REQUIRED ON)

# 开启严格的编译警告，高并发项目强烈建议开启，提前发现潜在 Bug
set(CMAKE_C_FLAGS "${CMAKE_C_FLAGS} -Wall -Wextra -g")

# 查找 pthread 库
find_package(Threads REQUIRED)

# ==========================================
# 1. 构建 Server 可执行文件
# ==========================================
# 明确列出 Server 所需的源文件
set(SERVER_SOURCES
    server/src/main.c
    server/src/server.c
    server/src/hash_map.c
)

add_executable(Server ${SERVER_SOURCES})

# 添加 Server 的头文件搜索路径
target_include_directories(Server PRIVATE
    ${CMAKE_CURRENT_SOURCE_DIR}/server/include
)

# 链接 pthread
target_link_libraries(Server PRIVATE Threads::Threads)


# ==========================================
# 2. 构建 Client 可执行文件
# ==========================================
# Client 1
add_executable(Client client/client.c)
target_link_libraries(Client PRIVATE Threads::Threads)

# Client 2
add_executable(Client2 client/client2.c)
target_link_libraries(Client2 PRIVATE Threads::Threads)
```

### 设计说明与解析：

1. **分离目标**：因为 `server` 和 `client` 是两个独立的可执行文件，所以分别调用 `add_executable`。这样修改了客户端代码后，只会重新编译客户端，不会连带编译服务端。
2. **`target_include_directories`**：这一步极其关键。`server/src/main.c` 中肯定包含了 `#include "server.h"`，如果不将 `server/include` 加入头文件搜索路径，编译器会找不到头文件。使用 `PRIVATE` 意味着这个路径只在编译 `Server` 时使用。
3. **多客户端支持**：你的 `client` 目录下有 `client.c` 和 `client2.c`，我将它们分别编译成了 `Client` 和 `Client2` 两个可执行文件，方便你后续做并发压测。
4. **编译警告 (`-Wall -Wextra`)**：在写 epoll 这种涉及复杂指针和系统调用的底层代码时，强烈建议开启严格警告。像未使用的变量、隐式类型转换等潜在隐患，编译器都会帮你指出来。

**对于你当前的项目规模，完全不需要分层设计。单根目录的一个 `CMakeLists.txt` 是最优、最清晰的选择。**

在 CMake 工程实践中，是否需要分层（使用 `add_subdirectory`）取决于项目的复杂度。下面为你详细梳理“什么时候用单目录，什么时候用分层”。

---

### 一、 为什么你现在不需要分层？

1. **文件数量少**：你的 `server` 只有 3 个源文件，`client` 只有 2 个。把这些文件路径直接写在根目录的 `CMakeLists.txt` 中，一眼就能看完，维护成本极低。
2. **避免过度工程化**：如果强行分层，你需要建 3 个 `CMakeLists.txt`，还要处理变量作用域传递（`PARENT_SCOPE`）等问题，这不仅没有减轻工作量，反而增加了阅读和调试的复杂度。这叫“杀鸡用牛刀”。

你目前根目录的那个写法，已经是非常标准且优雅的工程实践了。

---

### 二、 什么时候需要设计分层 CMake？

当你的项目满足以下条件之一时，才建议拆分成多个子目录的 `CMakeLists.txt`：

1. **模块化打包成独立库**：比如你的 `server` 中的 `hash_map.c` 变得极其庞大，或者你写了一个完整的 HTTP 解析模块，你想把它编译成一个独立的静态库（`.a`）或动态库（`.so`），不仅自己用，还要给别人用。
2. **源文件数量爆炸（>20个）**：根目录的 `add_executable` 里如果塞了几十个文件，列表会变得极长，难以维护。
3. **包含第三方子模块**：比如你把 `jsoncpp` 或 `protobuf` 的源码作为子目录放进去了，它们自带 `CMakeLists.txt`，你需要用 `add_subdirectory` 把它们拉进来一起编译。

---

### 三、 （拓展）如果未来要分层，长什么样？

假设几个月后，你的 `server` 越来越庞大，你想把核心逻辑抽离成一个静态库，然后再编译成可执行文件。那时候的架构才会变成这样：

```text
项目根目录/
├── CMakeLists.txt         【根目录：总调度】
├── server/
│   ├── CMakeLists.txt     【子目录：把核心逻辑打包成静态库】
│   ├── include/
│   └── src/
├── client/
│   ├── CMakeLists.txt     【子目录：编译客户端可执行文件】
│   └── client.c
```

**1. 根目录 `CMakeLists.txt` (总调度)**
```cmake
cmake_minimum_required(VERSION 3.20)
project(BigCSProject C)

# 添加子目录，CMake 会去执行子目录里的 CMakeLists.txt
add_subdirectory(server)
add_subdirectory(client)
```

**2. `server/CMakeLists.txt` (打包库)**
```cmake
# 把 server 下的文件打包成一个静态库 ServerCore
add_library(ServerCore STATIC
    src/server.c
    src/hash_map.c
)
# 暴露头文件给外部使用
target_include_directories(ServerCore PUBLIC include)
```

**3. `client/CMakeLists.txt` (链接库)**
```cmake
# 编译客户端
add_executable(Client client.c)
# 客户端如果也需要用到 hash_map，可以直接链接 ServerCore 库
# target_link_libraries(Client PRIVATE ServerCore)
```

### 总结
**CMake 的架构应该跟着代码架构走，而不是为了分层而分层。** 你现在的单 `CMakeLists.txt` 完全 hold 住全场，直接用现有的配置开始写 `epoll` 核心代码即可！
